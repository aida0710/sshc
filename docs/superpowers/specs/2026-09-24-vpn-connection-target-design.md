# VPNプロファイルから接続先を外す

## 目的

利用者の指示（2026-09-24）:

- 「vpn profileと接続先は分けたい。あくまでもパスワードみたいな感じで接続先にコネクションズから付与する感じ」
- macで`docker is not available: exec: "docker": executable file not found in $PATH`になった
- 「設定ファイルのmigration以外の下位互換性はいらないので、見つけたら削除してください」

直したあとに成り立たせたいことは次の4つである。

1. VPNプロファイルは、VPNへ接続するための設定とシークレットだけを持つ。接続先は持たない。
2. 接続先は、プロファイルを付けた接続（Connections）の`HostName`と`Port`で決まる。1つのプロファイルを
   複数の接続に付けられる。
3. macOS（Docker Desktop、OrbStack、colima）でも、Linuxと同じ仕組みで動く。
4. 設定ファイルの移行を除き、古い版のための分岐を持たない。

## 変えないもの

- VPNはプロファイルごとのコンテナの中にだけ存在する。ホストのルーティングもDNSも変えない。
- VPNの向こうのネットワーク全体は引き込まない。経路とパケットフィルタを作るのは、接続に使った
  接続先だけである。1つの接続先から、接続先の数だけに変わる。
- 接続先への通信はfail closedである。トンネル以外から接続先へ出る通信はコンテナの中で拒否する。
- 経路の寿命（10分の無操作で停止、どの入口の接続も数える）。
- Vaultの`vpn`レコードの形。

## 1. プロファイル

- `vpn.Profile`と保存形式（metadata.jsonの`vpnProfiles[]`）から`target`を消す。
- `dns`（VPN内のDNSサーバー）は残す。VPN内のホスト名を名前解決するための、VPNの設定だからである。
- 接続先がホスト名なのに、プロファイルにDNSサーバーが無い場合は、接続するときにエラーにする。
  Connectionsで付けるときにも、同じ条件なら注記を出す。
- 接続先はIPv4アドレスかホスト名に限る（今と同じ）。IPv6アドレスはエラーにする。
- VPNサーバーと同じアドレスの接続先はエラーにする（今と同じ）。

### 設定ファイルの移行

metadata.jsonの`schemaVersion`を5から6へ上げる。v5からv6への移行は`vpnProfiles[].target`を捨てるだけで、
接続とプロファイルの対応（`hosts[].vpn`）はそのまま残す。これまで各プロファイルの接続先に届いていた
接続は、移行後も同じ接続先へ届く（接続先が接続の`HostName:Port`と一致していなければ、v0.38.1では
そもそも繋がらなかった）。

版を上げるのは、v0.38.xが新しい文書を読んだときに、`target`の無いプロファイルを壊れた設定として
扱うためである。v0.38.xはv6の文書を読まずに止まる。

## 2. 接続に付ける

- 付ける場所はConnectionsの［sshc］タブの「使用するVPNプロファイル」と、`sshc vpn bind <alias> <名前>`。
- VPN画面は、プロファイルの作成・編集・接続・ログに絞る。どの接続が使っているかは一覧で見せるが、
  付け外しはしない（パスワードと同じく、付けるのは接続の側）。
- 接続先とプロファイルの食い違いの注記（`vpn_target_mismatch`）は、食い違いが起こらなくなるので消す。

## 3. 中継の仕組み

### いまの仕組みとその問題

コンテナの中の`socat`が、ホストと共有したディレクトリに`relay.sock`を作り、engineがホスト側から
つなぐ。宛先は起動時に1つに固定している。

- 宛先が1つなので、接続ごとに違う接続先へ届けられない。
- Docker Desktop for Macでは、コンテナの中で作ったUnixソケットにホストからつなげない（ファイルの
  共有を経由するため）。Windowsも同じである。

### 変えたあとの仕組み

接続1本ごとに、次を実行し、その標準入出力を接続として使う。

```text
docker exec -i <コンテナ> /usr/local/lib/sshc-vpn/connect <host> <port>
```

`connect`はコンテナの中で次を行う。

1. `host`がホスト名なら、プロファイルのDNSサーバーだけを使って名前解決する。
2. そのアドレスへの経路とパケットフィルタが無ければ足す（WireGuardでは`AllowedIPs`にも足す）。
   同時に2本来ても1回だけ足すよう、ロックを取る。
3. `socat STDIO TCP:<アドレス>:<port>`へ`exec`する。

失敗した場合は、理由の語（`target_unresolved`など）を標準エラーの最後の行に書いて終わる。engineは
それを読み、理由として返す。

- Linux、macOS、WindowsのDockerで同じ仕組みになる。Unixソケットの共有に頼らない。
- 接続を開くたびに`docker exec`の起動（数十〜数百ミリ秒）がかかる。SSHの接続時間に比べて小さいので
  受け入れる。
- 名前解決は、経路を起動してから初めてその接続先へ接続するときに1回行う。同じ経路の中では結果を
  使い回す。
- 「経路が使えるようになった」の合図は、`relay.sock`の代わりに`status.json`が現れることにする。
  `status.json`と`failure.json`は今と同じく共有ディレクトリに置く（通常のファイルなのでmacでも読める）。

### engineの中継（CLIと`sshc vpn proxy`）

`engine.sock`は残す。つないだ側は最初に`<host>:<port>\n`を1行送り、engineはその接続先へ
`docker exec`でつなぐ。1行の長さと待つ時間に上限を置く。

- `sshc <alias>`は、そのaliasの接続先を送る。
- `sshc vpn proxy <名前> <host> <port>`は`%h %p`を必須にする。接続先を持たないプロファイルでは、
  省略したときに行き先を決められないからである。

## 4. macOS

- dockerは、engineのPATHに無ければログインシェルのPATHで探す。launchdが起動したengineのPATHは
  `/usr/bin:/bin:/usr/sbin:/sbin`で、Docker Desktopの`/usr/local/bin`やHomebrewの`/opt/homebrew/bin`を含まない。
- ログインシェルのPATHの取得は、ProxyCommandのために作った仕組み（PR #87、未マージ）を`internal/platform`
  に共通化して使う。dockerを実行するときも、そのPATHを環境に渡す（`docker-credential-desktop`などの
  補助コマンドを見つけるため）。
- トンネル用のデバイス（`/dev/net/tun`、`/dev/ppp`）の有無はホストで確かめない。macOSではDockerの
  VMの中にあり、ホストには無い。`docker run`の失敗から判断する。
- エラーの文は日本語にし、dockerの生のエラーは詳細として後ろに付ける。

## 5. 下位互換の削除

設定ファイルの移行を除き、古い版のための分岐を消す。見つけたものは別の一覧にまとめ、この変更で
消す。例: `orphans.go`で、workspaceの札が無いコンテナ（v0.38.0）を止める分岐。

## 6. 確かめること

- 単体テスト: 移行（v5の`target`付き文書を読んで、v6で書く）、接続先の検査、`connect`の失敗の語の
  読み取り、engineの中継の1行目の上限。
- Dockerのテスト（`SSHC_VPN_DOCKER_TEST=1`）: 1つのWireGuardの経路で2つの接続先へ同時に届くこと、
  付けていない接続先へはコンテナの外へ出ないこと、名前解決の失敗の語が届くこと。
- macOSの実機は、このマシンでは確かめられない。利用者に確認を頼む。
