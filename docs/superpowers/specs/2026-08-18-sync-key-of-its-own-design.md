# 同期 (1) — 鍵をマスターパスワードから外す

いまリモートのスナップショットを封じているのは、このワークスペースの**マスター
パスワードそのもの**である。HTTP 層がそれを強制している。

```go
// internal/httpserver/sync.go
ok, err := h.Secrets.Verify(passphrase)   // マスターパスワードでなければ
case !ok:
    return false, problem(c, http.StatusForbidden, "wrong_master_password")
```

打ち間違いが誰にも開けない書庫を作るのを防ぐための検査であり、その目的には正しく
働いている。しかし副作用として、**マスターパスワードが端末をまたいだ共有秘密に
なっている**。

| やりたいこと | いまの結果 |
|---|---|
| 端末ごとに違うマスターパスワードを使う | できない。他端末がリモートを開けない |
| 1 台でマスターパスワードを変える | その端末が push した瞬間、他の全端末が締め出される |
| 人が居ないところで同期する | できない。毎回パスフレーズを打つ設計になっている |

3 行目が効いてくる。自動同期は、**打つ人が居ないときに封を開ける**ことだからだ。
鍵を人の記憶から出して、保管庫の中の値にしなければ始まらない。

## 方式 — 保管庫の中に、同期だけの鍵を 1 つ持つ

`secret.SyncSettings` は、すでにこの用途の器である。エンドポイント、バケット、
アクセスキー、シークレットが入っており、マスターパスワードから導出した鍵で封じ
られ、vault 本体とは別のファイルに置かれている（vault は同期で運ばれるので、
バケットへの鍵をバケットの中に入れないための分離である）。

同期の鍵もそこへ置く。**保管庫が開いていることが、同期してよいことの唯一の条件に
なる**——マスターパスワードは端末ごとのローカルな秘密に戻り、リモートを開ける鍵は
端末をまたいで共有される別の値になる。

```go
type SyncSettings struct {
    Endpoint        string `json:"endpoint,omitempty"`
    // ...
    Direction       string `json:"direction,omitempty"`
    // Key は、リモートのスナップショットを封じる値。マスターパスワードとは
    // 別物であり、端末をまたいで同じものを使う。
    Key             string `json:"key,omitempty"`
}
```

### 鍵の作り方

**既定は生成である。** 人が決めた文字列は、端末をまたいで共有される時点で、
どこかに書き留められる。書き留めるなら、覚えられる必要はない。

- `crypto/rand` から 15 バイト（120 ビット）。
- Crockford base32 で 24 文字。`I` `L` `O` `U` を含まないので、読み違いが起きない。
- 4 文字ずつ区切る: `AB12-CD34-EF56-GH78-JK90-MN12`。

`envelope.Derive` の下限（`MinPassphraseLength` = 12）は当然満たす。区切りの `-` は
そのまま鍵の一部である——表示された通りに入力すれば通る、が唯一の規則である。

**「自分で決める」も残す。** チェックを入れると入力欄に変わる。12 文字未満は
`envelope.ErrWeakPassphrase` がそのまま拒否する。既存のバケットを別の道具で作った
人や、鍵を自分の管理下に置きたい人のための逃げ道であって、既定ではない。

### 平文で外に出るのは一度だけ

生成した鍵は、生成した応答でだけ平文で返る。以後 `GET /api/v1/sync` が返すのは
「設定されているか」だけである。**リモートを開ける値を、状態を読むたびに配る API に
してはならない。**

## API

| いま | これから |
|---|---|
| `POST /sync/push` `{passphrase}` | `POST /sync/push` 本文なし |
| `POST /sync/pull` `{passphrase, apply}` | `POST /sync/pull` `{apply}` |
| — | `PUT /sync/key` `{key?}` → `{key}` |
| — | `POST /sync/rekey` `{passphrase}` |
| `SyncStatus` | `SyncStatus` に `keyConfigured: boolean` |

`PassphraseRequest` は保管庫の作成・解錠と共用のスキーマなので、push からは外す
だけで手を触れない。

**`PUT /sync/key`** は、本文が空なら生成し、`key` があればそれを採用する。応答は
どちらの場合も採用された鍵そのものである（画面はこれを一度だけ見せる）。

**`POST /sync/rekey`** は移行のためにある。下の「移行」を見よ。

権限は「保管庫が開いていること」に移る。鍵は保管庫の中にあり、保管庫を開けるのは
マスターパスワードを知っている人だけである——`masterPassword()` の検査は、この
一段で置き換わる。

## 画面

`SyncPanel` の「パスフレーズ」欄（push と pull のたびに打っていたもの）を消し、
設定の節に「暗号化キー」を置く。

```
暗号化キー
  未設定:   [キーを作る]   □ 自分で決める
  作った直後: AB12-CD34-EF56-GH78-JK90-MN12   [コピー]
             他の端末では、この文字列を同じ欄に入力します。
             ここを離れると二度と表示されません。
  設定済み:  ••••-••••-••••-••••-••••-••••   [置き換える]
```

push と pull のボタンからは入力欄が消え、押せる条件は「バケットが設定済み」かつ
「鍵が設定済み」になる。

## 移行 — 既存のリモートは古い鍵で封じられている

いまバケットにあるオブジェクトは、マスターパスワードで封じられている。新しい鍵で
開こうとすれば `envelope.ErrWrongPassphrase` になる。

`POST /sync/rekey` が、その一度きりの橋を架ける。

1. リモートのライブオブジェクトを取得する。
2. 与えられた**古い**パスフレーズで開く。開かなければ 403 `wrong_passphrase` で、
   ローカルには何も起きない。
3. 中身はそのまま、**新しい鍵で封じ直して**、同じ ETag を条件に書き戻す。
4. 条件が合わなければ 409 `remote_moved`。他端末が間に入ったということなので、
   もう一度やればよい。

ワークスペースには 1 バイトも触れない。失敗しても、リモートは元のままである。

他の端末では、新しい鍵を入力するだけでよい。**鍵を替えた端末が push し直す必要は
ない**——封を替えるのはこの操作自身だからだ。

## エラー

| 状態 | 応答 |
|---|---|
| 鍵が未設定のまま push / pull | 409 `sync_key_missing` |
| 保存された鍵でリモートが開かない | 403 `wrong_passphrase`（画面は移行を案内する） |
| 自分で決めた鍵が 12 文字未満 | 400 `passphrase_too_short` |
| 保管庫が閉じている | 409 `vault_locked` |

`wrong_master_password` は sync からは消える。保管庫の解錠が使っているものは残る。

## テスト

**Go**

- 生成した鍵が 24 文字 + 区切りであること、`I L O U` を含まないこと、二度呼んで
  同じ値が出ないこと。
- `PUT /sync/key` が保管庫に書き、`GET /sync` が値ではなく `keyConfigured` だけを
  返すこと。**応答本文に鍵が混ざらないことを明示的に assert する。**
- push / pull が、リクエストではなく保管庫の鍵を使うこと。
- 鍵未設定での push / pull が 409 で、リモートにもディスクにも何も起きないこと。
- rekey が、古い鍵で開いて新しい鍵で封じ直し、ETag の条件を守ること。ワークスペース
  に触れないこと。
- rekey が古い鍵を間違えたとき、リモートが元のままであること。

**Web**

- パネルの状態遷移（未設定 → 生成 → 一度だけ表示 → 伏せ字）。
- push / pull がパスフレーズを送らないこと。
- 鍵が未設定のとき、push / pull が押せないこと。

**e2e**

既存の sync spec を、パスフレーズ入力の消えた形へ更新する。

## スコープ外

- **鍵のバックアップと、壊すときの確認**（サブ 2）。いま pull は秘密鍵を
  `SkipBackup` で書き換えるので取り消せない。自動化の前に閉じる。
- **自動同期**（サブ 3）。この文書が作るのは、その前提である「人が居なくても開く
  鍵」だけである。
- 鍵を OS のキーチェーンへ逃がすこと。保管庫が開いている間だけ同期する、と決めた
  ので要らない。
