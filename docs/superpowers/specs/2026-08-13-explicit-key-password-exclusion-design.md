# 明示した秘密鍵と保存済みログインパスワードの排他化

## 目的

接続の具体的な `Host` ブロックに秘密鍵が設定されている場合、sshc はその接続へ
保存済みログインパスワードを割り当てず、接続時にも自動入力しない。鍵が失敗した後の
手入力、keyboard-interactive、ワンタイムコードなどは OpenSSH クライアントと
サーバーの標準的な認証交渉へ任せる。

これにより Connections の認証欄を「選択した鍵」と「その鍵を解錠するための
パスフレーズ」へ絞る。鍵認証に、別用途であるログインパスワードの状態・操作・警告を
常時併記しない。

この仕様は、接続概要の従来仕様にある「鍵とログインパスワードを独立した有効な項目と
して同時表示する」という部分、および鍵がある接続へのパスワード保存を warning のみで
許可する部分を置き換える。鍵パスフレーズとリモートアカウントのパスワードが異なる
秘密であるという保存境界は変更しない。

## 認証モデル

保存済みログインパスワードを使用できるかどうかは、選択中の具体的な `Host` ブロックに
直接 `IdentityFile` があるかで決める。

- inventory から選んだ鍵、独自パス、複数の直接 `IdentityFile` は、すべて「明示鍵あり」
  とする。
- OpenSSH の特殊値 `IdentityFile none` だけは鍵を指定していないため、明示鍵に数えない。
  複数値の中に `none` 以外が一つでもあれば明示鍵ありとする。
- `Host *`、別の一致ブロック、`Match` などから継承した鍵、および ssh-agent の鍵は
  明示鍵に数えない。
- `CertificateFile`、`IdentityAgent`、`IdentitiesOnly` だけでは明示鍵ありにしない。

したがって「SSH agent または継承した鍵」を選んだ接続では、従来どおり専用・既存共有・
新規共有の保存済みログインパスワードを使用できる。sshc がその接続へ具体的な鍵を
割り当てた場合だけ、ログインパスワードと排他にする。

sshc は `PasswordAuthentication no`、`PreferredAuthentications`、`BatchMode` などを
追加しない。保存済みパスワードを渡さない接続は、askpass を武装せず通常の `ssh` として
起動する。そのため OpenSSH が必要と判断した手入力、鍵のパスフレーズ、2FA、
keyboard-interactive は引き続き利用できる。

## Connections の表示

### 明示鍵がない場合

SSH 秘密鍵の選択欄に続けて、現在の保存済みログインパスワードの状態と操作を表示する。
既存の専用パスワード、名前付き共有パスワード、新しい共有パスワード、割り当て解除の
機能は維持する。

### 明示鍵がある場合

SSH 秘密鍵の選択欄の直下には、その鍵の状態だけを表示する。

- 暗号化されていない鍵: 「この鍵は暗号化されていません。パスフレーズの保存は不要です」
  と短く表示する。独立した「保存済みの鍵パスフレーズ」見出しは置かない。
- 暗号化済みで未保存: 鍵パスフレーズが未保存であることと、保存・確認入力を表示する。
- 暗号化済みで保存済み: 専用または名前付きの安全な状態だけを表示し、置換入力を表示する。
- 独自パスまたは複数の直接鍵: 従来どおり基本タブでは読み取り専用とし、詳細タブへの案内を
  表示する。鍵パスフレーズ編集は表示しない。

通常は次を表示しない。

- 保存済みログインパスワードの状態
- 保存済みログインパスワードの操作
- 「鍵と保存済みパスワードは独立しています」という説明
- 鍵があることを理由とするパスワード保存 warning

鍵が未選択の下書きから鍵を選ぶと、ログインパスワード操作と入力済みの秘密値を即座に
画面から消し、メモリ上の入力値も消去する。同じ保存済み選択へ戻した場合は削除予約も
取り消し、保存済みパスワード操作を復元する。消した秘密入力を復元・再表示してはならない。

## 既存の矛盾した割り当て

アップグレード前のデータや Raw 編集によって、明示鍵と保存済みログインパスワードが
同じ接続に存在することはあり得る。この場合、パスワードを有効な認証方法として表示せず、
認証欄に次の安全な metadata だけを表示する。

> この接続には保存済みパスワードが割り当てられています。sshc は使用しません。
> 基本設定を保存すると割り当てを解除します。

この cleanup はフォームの dirty state に含める。ほかに変更がなくても「基本設定を保存」を
有効にし、追加の確認 checkbox は要求しない。保存前に鍵選択を元へ戻した場合、cleanup は
取り消す。下書きの破棄、画面移動、保存失敗では vault を変更しない。

保存成功時の扱いは次のとおりとする。

- 接続専用パスワードは、その接続の値を削除する。
- 名前付き共有パスワードは、この接続との関連だけを解除する。資格情報本体とほかの利用者は
  変更しない。
- 鍵用パスフレーズは維持する。

ConnectionSummary は通常の明示鍵接続でアカウントパスワード行を表示しない。矛盾した
割り当てがある間だけ「割り当てあり・未使用・保存時に解除」と表示し、実際に自動入力される
かのような表現をしない。Secrets の利用先一覧には、cleanup が保存されるまでは従来どおり
関連が見える。

## 保存のサーバー境界

ブラウザーの表示だけでは旧クライアントや API の直接呼び出しを防げないため、サーバーが
更新後の具体的な `Host` ブロックを正本として排他条件を強制する。

1. 更新後に明示鍵があり、password mutation が追加・置換・再割り当てなら、
   `password_ineligible` として全体を拒否する。
2. 同じ request で直接 `IdentityFile` を継承へ戻し、パスワードを追加・割り当てする操作は
   許可する。継承先に鍵があってもこの判断は変えない。
3. 更新後に明示鍵があり、既存パスワード割り当てが残っていれば、password が
   `unchanged` でもサーバーが removal を同じ transaction に加える。
4. cleanup だけでも実変更として保存できる。既存割り当てがなければ不要な vault 再封印や
   journal を行わない。
5. config、vault、履歴、live memory は現在の atomic connection update と同じ commit に
   含める。検証・外部変更・書込みの失敗時はすべて不変にする。
6. cleanup が必要なのに vault の正しい状態を確認・変更できない場合、config だけを保存せず
   全体を拒否する。

connection update 以外の既存パスワード保存 API も迂回口にしない。
`PUT /api/v1/passwords/{alias}` と password kind の credential assignment は、現在の
specific `Host` block に明示鍵があれば同じ eligibility blocker で拒否する。
key-passphrase kind の assignment には適用しない。eligibility の
`identity_file_configured` は warning から blocker へ変更し、継承鍵ではなく直接値の
source location を返す。旧 PasswordPanel のような呼び出し元が残っていても、サーバー境界は
同じである。

Raw・任意ディレクティブ編集の transaction に vault mutation は追加しない。これらの経路で
明示鍵が追加された場合も、次節の接続時境界が直ちにパスワード自動入力を止める。基本設定を
次に保存した時点で関連を cleanup する。この限定は Raw 保存の既存トランザクションを別の
秘密管理機能へ拡張しないためである。

## 接続時のサーバー境界

保存済みパスワード用トークンを発行するすべての入口は、発行直前の config から直接
`IdentityFile` の有無を再判定する。対象は少なくとも次を含む。

- `sshc <alias>` と `sshc connect` が使う CLI 接続入口
- Home と Connections の Terminal 起動

明示鍵がある場合は、古いパスワード関連が vault に残っていてもトークンを発行しない。
接続自体は拒否せず、パスワードなしの通常経路で OpenSSH を起動する。config の読取りまたは
判定に失敗した場合も秘密を渡す側へ倒れず、トークンを発行しない。エラーは安全な warning と
して表示できるが、alias にパスワードがあるかどうかを CLI 接続ルートの外部へ漏らさない。

接続要求とトークン発行の間、およびトークン発行と redeem の間に config が変わる可能性が
ある。発行時だけでなく redeem 時にも同じ alias の明示鍵判定を行い、後から鍵が追加された
場合は未使用トークンを拒否して消費する。これにより、発行済みトークンが新しい設定を越えて
パスワードを返すことを防ぐ。

「保存済み設定で認証を確認」は現在も `BatchMode=yes`、
`NumberOfPasswordPrompts=0`、askpass なしの非対話試験であり、保存済みログインパスワードを
使用しない。この仕様で挙動を変えたり、パスワードを使う検査へ広げたりしない。

## エラーと秘密情報の扱い

- 排他違反は既存の具体的な `password_ineligible` problem としてフォーム付近へ表示する。
- cleanup の保存失敗は「何も変更されていない」と表示し、パスワード名・値を problem、diff、
  preview、ログへ含めない。
- 鍵を選んだ時点、保存成功、保存失敗、破棄、接続変更で、不要になったログインパスワード入力を
  メモリと DOM から消す。
- URL、history、localStorage、sessionStorage へ認証状態や秘密を追加しない。
- 手入力や2FAを sshc が識別・保存・自動回答する機能は追加しない。

## テスト

### Application / secret / HTTP

- 直接の inventory 鍵、独自パス、複数鍵を明示鍵と判定する。
- `IdentityFile none`、継承鍵、ssh-agent を明示鍵と判定しない。
- 明示鍵を残したパスワード追加・置換・再割り当てを API が拒否する。
- standalone password store と password credential assignment も明示鍵で拒否する。
- 鍵の継承化とパスワード割り当てを一 transaction で許可する。
- 鍵設定と既存専用パスワード削除を一 transaction で commit する。
- 共有パスワード cleanup が対象 alias だけを外し、他利用者と資格情報本体を維持する。
- cleanup だけを保存でき、割り当てなしの同値 request は no-op のままにする。
- 各 commit failure で config、vault、履歴、live clone がすべて不変である。
- CLI と Terminal の各入口が、明示鍵のある alias へトークンを発行しない。
- 発行後に鍵が追加されたトークンを redeem できず、そのトークンが再利用できない。
- config 判定失敗時はトークンを発行せず、レスポンスとログに秘密 metadata を漏らさない。

### Web

- 明示鍵なしの場合だけログインパスワード状態と操作を表示する。
- 暗号化されていない鍵では短い説明だけを表示する。
- 暗号化鍵では鍵パスフレーズ状態と入力だけを表示する。
- 独自パスと複数直接鍵でもログインパスワード操作を表示しない。
- 鍵選択時に入力済みログインパスワードを DOM と request state から消す。
- 鍵選択を元へ戻すと cleanup dirty state が消えるが、消去済み秘密値は復元しない。
- 既存の矛盾した専用・共有割り当てを未使用 cleanup として表示し、ほかに変更がなくても
  保存できる。
- cleanup 保存失敗と refresh 失敗を区別し、秘密を再表示しない。
- ConnectionSummary が有効でないアカウントパスワードを通常状態として表示しない。

### End-to-end / integration

- 明示鍵のある接続で不要なログインパスワード欄が表示されない。
- 古い併存データを読み、基本保存で専用削除または共有関連解除を行う。
- 鍵接続では保存済みパスワードを自動入力せず、OpenSSH の手入力経路を残す。
- 鍵のないパスワード接続は従来どおり Docker sshd に認証できる。
- 鍵を外してパスワードを割り当てる一括更新が、次の実接続で機能する。

最終検証は generated API、Go normal/race、Web unit、TypeScript、production build、
Playwright、Docker SeaweedFS/sshd integration を含む。

## 非目標

- OpenSSH の認証順序を sshc が固定すること。
- パスワード手入力、keyboard-interactive、2FA を禁止すること。
- 2FA、OTP、PAM prompt を保存または自動入力すること。
- 継承鍵や ssh-agent と保存済みパスワードを排他にすること。
- Raw・任意ディレクティブ保存を vault transaction へ拡張すること。
- 鍵パスフレーズとリモートアカウントのパスワードを同じ資格情報として扱うこと。
- 既存 vault を起動時に一括 migration して関連解除すること。
