# 端末レンダラーの評価記録

結論: 独自レンダラーは現時点では実装しません。段階 1 の依存整理だけを実施しました。

実装判断のために段階 0 の性能測定まで実施しました。現行レンダラーに実用上の問題が
見つからなかったため、段階 2 以降は保留します。以下に判断根拠と再評価時の確認項目を記録します。

## 対象範囲

端末は次の 2 層に分けて扱います。

| | 中身 | どうするか |
|---|---|---|
| 解釈 | ANSI/VT の解析、画面状態、モード、スクロール領域、代替画面 | xterm.js を継続使用 |
| 描画 | 状態から画面を生成 | 独自実装を検討したが保留 |

`Terminal.write()` の内部で xterm.js が ANSI/VT を解釈します。CJK の文字幅、結合文字、
DEC 線描画、`vim`、`tmux`、`top` の表示互換性はこの層が提供します。この層は変更対象にしません。

## 内部に触らない

xterm の描画 addon（canvas / webgl）は `_core` の非公開 API を使用します。上流の変更に
追随する保守コストを避けるため、独自実装では非公開 API を使用しません。

代わりに、次の公開 API だけを使用できることを確認しました。

```
buffer.active.getLine(y).getCell(x) →
  getChars() getCode() getWidth()
  getFgColor() getFgColorMode() isFgRGB() isFgPalette() isFgDefault()
  getBgColor() getBgColorMode() isBgRGB() isBgPalette() isBgDefault()
  isBold() isDim() isItalic() isUnderline() isOverline()
  isBlink() isInverse() isInvisible() isStrikethrough()
buffer.active.cursorX / cursorY / viewportY / baseY / length
```

全角文字の幅には `getWidth()` を使用し、独自に計算しません。

## `.xterm-rows` への依存（段階 1 の実施前）

レンダラーを変更すると xterm が生成する span はなくなります。依存箇所を調査したところ、
テストだけでなく製品コードにも参照がありました。

| 場所 | 何を読んでいたか |
|---|---|
| `e2e/terminal.spec.ts` 4 箇所、`e2e/narrow.spec.ts` 3 箇所 | 字と、寸法・字体 |
| `src/terminal/selectionOverlay.ts` | `letter-spacing` などのフォント設定 |

`selectionOverlay` は文字を `buffer` の `viewportText` から取得しますが、フォント設定は
`getComputedStyle(.xterm-rows)` から取得していました。xterm は「1 セルの幅から実測した W の幅を引いた値」を
`letter-spacing` に設定するため、この値を適用しないと列位置がずれます。

段階 1 でこの処理を `metrics.ts` に移し、製品コードから xterm DOM を参照する箇所を集約しました。
当時、残っていた参照は E2E テストの 7 箇所でした。

独自 canvas レンダラーでは `letter-spacing` を使用せず、各セルを `x * セル幅` に配置します。
その場合は外部スタイルの取得が不要になり、オーバーレイへ計測値を直接渡せます。

（位置と大きさは `.xterm-screen` から取っており、そちらも `metrics.ts` に入った。）

## 順序

各段階は個別にリリースでき、後続段階を実施しなくても成立するように分けます。

### 0. 性能測定（完了）

xterm 6.0.0 の DOM 描画に、実物と同じ設定（120x30・32 KiB ずつ・scrollback 5000）で
50,000 行を一気に流した。中央値、3 本。

| 負荷 | 解析のみ | 解析+描画 | **描画のぶん** | 行/秒 | 最悪の 1 フレーム |
|---|---|---|---|---|---|
| ログを cat | 118ms | 168ms | **50ms** | 298,000 | 18ms |
| 色付きビルド出力 | 230ms | 289ms | **58ms** | 173,000 | 22ms |
| top 風の全画面 | 263ms | 284ms | **21ms** | 176,000 | 24ms |
| 日本語 | 87ms | 140ms | **53ms** | 358,000 | 18ms |

描画時間は全体の 12〜25% で、最も遅いフレームは 17〜24 ms でした。測定中に UI の停止は発生しませんでした。

#### CJK 測定の訂正

最初の測定では日本語の描画だけが 1518 ms（他の約 30 倍）でした。調査の結果、測定環境に
日本語フォントがありませんでした（`fc-list :lang=ja` が 0）。この値はフォント探索の時間であり、
日本語描画の性能を示していません。

Noto Sans Mono CJK JP を追加して再測定した結果が上の表です。日本語と ASCII に有意な差はありませんでした。

#### 低速 CPU での結果

Android など低性能端末の条件に近づけるため、CPU を制限して 20,000 行を測定しました。

| 絞り | 負荷 | 解析+描画 | 描画のぶん | 最悪の 1 フレーム |
|---|---|---|---|---|
| 4x | 色付き | 964ms | 587ms（61%） | 44ms |
| 8x | 色付き | 3183ms | 2108ms（**72%**） | **142ms** |
| 8x | ログ | 961ms | 431ms（45%） | 35ms |
| 8x | 日本語 | 1075ms | 685ms（64%） | 56ms |

CPU 制限を強くすると描画時間の比率が増えました。最も遅いフレームは 142 ms でした。

#### canvas の基礎性能

同じ 64,800 セル（xterm が 50,000 行の処理中に実際に描画した量）を canvas に
`fillText` で描画すると 82〜105 ms でした。20,646 種の文字や日本語を混ぜても結果は変わりませんでした。

#### WebGL は、ここでは測れなかった

同じ条件では WebGL アドオンが 3〜7 倍遅い結果になりました。ただし、この環境は GPU ではなく
`ANGLE (SwiftShader)` による CPU 描画でした。この値は実機性能の判断には使用せず、Mac と Android 実機での再測定まで保留します。

### 判断

独自レンダラーは実装せず、段階 2 以降を保留します。

- 手元では描画は律速ではない（12〜25%、コマ落ちなし）
- 日本語も速い。遅く見えたのは計測環境の欠陥だった
- 低速 CPU では描画が 72% を占め、最も遅いフレームは 142 ms だったが、全面的な再実装を正当化する問題は確認できなかった

段階 1 は、レンダラーの実装判断に関係なく保守性を改善するため実施しました。寸法とフォント情報の取得元を
1 箇所に集約したため、製品コードでレンダラー変更時に修正する箇所は `metrics.ts` だけです。

> 2026-08-23 追記: テスト側の集約も完了しました。`web/e2e/support/terminal.ts` が
> spec 内の `.xterm-*` 参照を集約します。`metrics.test.ts` は E2E spec からの直接参照も検出します。

将来の最小変更案は WebGL アドオンの導入です。変更対象は製品側の `metrics.ts` と
テスト側の `support/terminal.ts` の 2 ファイルに限定されています。

依存の集約自体は canvas レンダラーを実装しませんが、レンダラーの性能評価に必要な変更量を減らします。

再評価条件: Android 実機で描画遅延が報告された場合。まず WebGL アドオンを実機で測定し、
それでも要件を満たさない場合に独自実装を検討します。

### 1. セル寸法の取得元を集約（完了）

`src/terminal/metrics.ts` を追加し、xterm DOM の参照をこのファイルに集約しました。

変更前は 2 箇所が別々に行の高さを計測していました。

| 場所 | 導出 |
|---|---|
| `selectionOverlay` | `getBoundingClientRect().height / rows`（端数を持つ） |
| `TerminalView` | `clientHeight / rows`（整数に丸められる） |

境界線と padding がない現在は同じ値になりますが、API 上の保証はありません。
タッチスクロールは 1 行未満の移動量を蓄積するため、小数を保持する計測方法に統一しました。

`getComputedStyle(.xterm-rows)` の参照も `measureCells()` に移しました。
`selectionOverlay` は xterm DOM の構造に依存しません。

`metrics.test.ts` は、xterm DOM の参照が許可したファイル以外に追加された場合に失敗します。
`touchScroll.ts` に参照を追加してテストが失敗することも確認しました。

#### テスト側の集約に関する当初の判断

当初は、レンダラー変更時にテストが xterm DOM の変更だけで失敗しないようにすることが目的でした。
段階 0 でレンダラー変更を保留したため、この作業もいったん保留しました。

製品コードにテスト専用の文字取得 API を追加する案は採用しませんでした。
その後、2026-08-23 に製品 API を増やさず、E2E の参照だけを `support/terminal.ts` に集約しました。

当時の変更候補は E2E テストの 7 箇所でした。

| 読んでいるもの | 箇所 |
|---|---|
| 字（`toContainText` / `innerText`） | narrow 2、terminal は `region` 経由で間接的に |
| 寸法（`boundingBox` / `children.length`） | terminal 4 |
| 字体（オーバーレイとの一致） | narrow 1 |

フォント設定の 1 件は、`metrics.ts` が取得した値を実ブラウザで検証するため、E2E テストに残します。

### 2. xterm と canvas を並行描画する

xterm を従来どおり `open()` し、その上に canvas を重ねて同じ内容を描画します。
両方を比較して差異を修正します。

見るもの: 字体と行間、前景と背景、太字・斜体・下線・反転、カーソルの形と点滅、
全角の桁送り、選択の帯。

この段階の完了条件は、xterm と canvas の表示が一致することです。性能改善は完了条件に含めません。

### 3. xterm の描画を止める

表示が一致したら、xterm 側の描画を非表示にします。段階 1 の計測値は、xterm の DOM ではなく独自レンダラーから取得するように変更します。

`.xterm-rows` への依存は段階 1 で集約済みのため、この段階の変更範囲を限定できます。

### 4. 差分描画へ移行する

`onRender` が通知する変更行だけを再描画し、毎回の全画面描画を避けます。

### 5. GPU（要るなら）

2D canvas の性能を測定し、要件を満たさない場合にだけ WebGL を検討します。

## 実装上の確認項目

- フォント計測: セル幅と行高。等幅フォントでも合字や絵文字でずれる可能性がある。段階 1 で取得箇所を集約済み
- DPR: 拡大表示でぼけないこと。外部モニターへの移動などで `devicePixelRatio` が変化する
- スクリーンリーダー: xterm の DOM を削除する場合は読み上げ機能を実装する必要がある。`aria-hidden` にはせず、視覚的にだけ非表示にする方が変更量は少ない
- IME: `imeKeys.ts` は入力側の処理だが、レンダラー変更後も動作確認が必要
- リンク: 現在は未使用。導入時には独自のヒットテストが必要

## 中止条件

段階 2 で xterm と canvas の表示を一致させられない場合は中止します。不一致のまま段階 3 へ進めません。

段階 0 で現行レンダラーの問題を確認できなかったため、現時点では段階 1 までで終了します。

## 再測定時の注意事項

- CJK フォントがない環境ではフォント探索時間が加算され、結果が約 30 倍になった。測定前に `fc-list :lang=ja | wc -l` を確認する
- xvfb の WebGL は SwiftShader を使用するため、GPU 性能を測定できない。`WEBGL_debug_renderer_info` で renderer を確認する
- 負荷は文字数やバイト数ではなく、端末が描画するセル数で揃える。全角文字は 1 文字で 2 セルを使用する
